SecOps Universal Connector Framework · test reference

Every part of it, and how to prove it works

Five capabilities, five inbound routes, four handlers and a staging pipeline. Below: what each one does, a payload you can paste straight into Postman, the external tools it can talk to, and the internal behaviour that no HTTP client can reach.

Every URL on this page updates as you type. Stored in this browser only.

What the application does

5 capabilities

You describe a third-party tool as records — a connector (who and where), endpoints (callable operations), and optional field mappings (which part of the response lands on which field). Four handlers drive those records. Onboarding a new tool is data entry, not code.

Threat intel enrichmentSecOpsThreatIntelHandler
Calls every active enrich endpoint for one observable, writes a Threat Lookup Result per source, rolls the worst verdict up. It will not lower an existing verdict and will not override a manual analyst decision — so a feed that changes its JSON shape cannot erase a known-bad finding.
Phishing responseSecOpsPhishingHandler
Harvests IOCs from a security incident — including journal fields, and re-fanging hxxp:// and 1.1.1[.]1 — detonates each, returns the worst disposition. "Nothing malicious" and "the sandbox is down" do not look alike.
Vulnerability ingestionSecOpsVulnIngestionHandler
Push (inbound REST) or pull (scheduled). Always stages first — never writes straight into Vulnerability Response. De-duplicates on source + external id, resolves CIs in two queries per batch, and leaves an ambiguous CI match empty rather than guessing.
ContainmentSecOpsContainmentHandler
Isolate, release, block, unblock — against a host, IP, user, URL, hash or account. A request that cannot name its target is refused before any HTTP happens, and the requester and reason are logged before the call, not after.
Connection healthSecOpsHealthChecker
Hourly sweep, a Test button, and a REST route. A 4xx is degraded, not down — the service answered, so it is up and the credential is wrong. No answer at all is down.

Everything is logged, with credentials removed

Every outbound call writes a transaction row with the request and response redacted first. Keys matching password, secret, client_secret, api_key, token, authorization, x-api-key — plus anything you add — become ***REDACTED***. Redaction fails closed: a structure nested past the depth limit is replaced wholesale rather than passed through.

What it deliberately will not do

Not thisBecause
Store a credentialThey live in Connection & Credential Aliases and resolve at call time
Write into VR by defaultVR is a separate subscription; the app must install and run without it
Replay a failed requestThe only stored copy is redacted, so a replay would send a broken request
Refresh an OAuth token itselfA blind retry on a dead grant can lock out the service account. It reports the fix instead.
Sleep between retriesScoped apps have no gs.sleep(). Back-pressure is parked for a scheduled job.

Inside the phishing handler

the one that chains three subsystems

Think of a mailroom X-ray desk: read the whole report including the sticky notes attached to it, highlight every identifier, send each to the lab, file an evidence card per item, staple the cards to the case file, and report the worst single result rather than an average.

Why each step is written the way it is

StepThe reason it is not simpler
Journal fields read with getJournalEntry(-1) comments and work_notes store content in sys_journal_field, so getValue() returns the empty journal input. A forwarded phish usually arrives as a comment — getValue() would drop the most common place the evidence lives, and the handler would report success having found nothing.
Longest hashes matched first A 64-character hex string contains 32-character substrings. Domains are matched last, against text with URLs and emails already stripped, so one string is never reported twice under two types.
IPv4 validated, not just regex-matched Rejects octets above 255 and zero-padded forms like 01.1.1.1 — but deliberately accepts 1.2.3.4. That is a valid dotted quad, and deciding it is "probably a version string" would be the wrong kind of clever.
Cap of 15, with its own property Each indicator is one synchronous outbound call. A report pasted with a full header block can yield fifty; fifty sequential calls in one transaction exhausts the quota and leaves an incident half-processed. Truncation sets outcome.truncated rather than staying quiet.
finding written on insert only Re-analysing the same phish coalesces onto the existing observable. Writing the verdict unconditionally would fail twice over: a failed detonation returns Unknown, erasing a previous Malicious, and it would ignore an analyst's manual override. Existing observables route through rollUpFinding(), which refuses both.

The gotcha

Field mappings on a detonate endpoint do nothing — unless target_field is finding.

processIndicator calls the base handler with write: false, because the handler writes the observable itself. That skips mapAndWrite() entirely. The only place mappings are read is inside findingFrom(), which scans for one targeting finding and ignores every other row.

So sandbox_verdict → finding works exactly as expected, and anything else on the same endpoint is configured, saved, executed — and silently does nothing. On an enrich endpoint those same rows would override the default value set. Same configuration table, different behaviour per capability.

Also worth knowingWhat to check instead
ok: true with zero indicators is a real outcome — nothing was analysed, but nothing failedoutcome.indicators.length
ok means "at least one indicator was analysed", not all of themoutcome.indicators[].ok
A failed detonation gives Unknown, never Cleanoutcome.disposition plus the transaction's status

Scripts - Background

Set the scope selector to "SecOps Universal Connector Framework" first. The infrastructure script includes are package_private, so in global scope these fail with SecOpsJson is not defined. Only the five handlers are public.

Verdict monotonicity — the most important one

This is the rule that stops a broken feed erasing a known-bad verdict. If any downgrade below succeeds, treat it as a stop-ship bug.

obs.initialize()

Retry and back-pressure

Point an endpoint at https://httpbin.org/status/429 with max_retries: 2. The transaction should show retry_count: 2, state: retry_pending and a next_retry five minutes out. Then run the Expire deferred retries job after that timestamp: the state must become failed with the reason appended. A 500 behaves differently — retryable, but not back-pressure, so it fails immediately with no next_retry. Confirm both.

The business rules

Both ship inactive and gated by x_335329_secops.enrichment.auto_enabled. Two independent switches, because enabling automation that spends a customer's API quota should never be a side effect of installing an app. Test both directions: rule active + property off must do nothing.

If enrichment silently writes nothing

Check System Applications → Application Restricted Caller Access for a pending entry. SIR runs with RCA on, and the writer degrades gracefully rather than throwing — so a denial looks like "nothing happened", not like an error. That is the first place to look.

The harmless self-test
